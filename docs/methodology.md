### 1.4 这份数据为什么有价值

- **发现渠道分布本身就是结论**：49% 的错误是用户当场抓出的；另有 348 条是"当时没人发现、事后挖掘才翻出来"的漏检。这说明**自动质检存在结构性盲区**——只盯"检查通过"会系统性漏掉一半。

- **全部教训来自真实工作场景**（不是构造的测试集），且每条都有唯一键可回溯，支持"错误→规则→回流→复发计数"的闭环度量。

## 2. 四层防线（设计视图）

### 2.1 分层职责

| 层 | 回答的问题 | 关键机制 | 失效模式 |
|---|---|---|---|
| **L1 注入层** | 它知道规则吗？ | 全局记忆铁律（少而精、位置前置）、指针行＋红线最小集（≤6 条）、条件注入、双周治理 | 规则稀释、位置衰减、压缩蒸发、静默加载失败、陈化污染 |
| **L2 流程层** | 它会照做吗？ | 六栏任务合同（完成线由合同下发）、开工先读清单、教训卡模板、步骤化 skill、交付前 GATE 协议 | agent 自拟完成线、跳过验证步骤 |
| **L3 强制层** | 不照做会怎样？ | hooks/CI 质量门、确定性拦截（fail-closed）、结构化合同字段与 verdict 门 | hook 默认 fail-open、门禁被绕过 |
| **L4 审计层** | 下次还犯吗？ | 独立评审（审核者≠生产者、新鲜上下文）、rubric 逐项取证、错误台账、教训回流、记忆治理 | judge 自偏好、审核器漂移（发现率异常先审审核器） |

### 2.2 与"三道防线"运行视图的对应

日常运行时讲"三道防线"，设计文档讲"四层防线"，是同一体系的两个视图：

```
运行视图                              设计视图
第1道 记忆注入（全局记忆铁律）    ≈   L1 注入层
第2道 合同+清单+审核员           ≈   L2 流程层 ＋ L3 强制层 ＋ L4 审计层
第3道 人工把关（owner Approve）  ＝   终裁闸门（高风险动作的最后一道）
回流循环                          ＝   贯穿四层：L4 发现的教训规则化进 L1/L2/L3
```

### 2.3 十条设计公理（每条可追溯到公开研究或本仓库 839 条实证）

1. **证据先于断言**：没有本轮新鲜运行的验证证据，不得声称完成；跳步骤的"检查"等于说谎。
2. **检查者与生产者隔离**：审核员独立上下文，只拿交付物＋验收标准＋易错点清单，不携带生产会话史。
3. **检查项必须可机器执行、输出留痕**：结构化证据（命令/退出码/输出摘录），不接受叙述性"已完成"。
4. **规则预算制**：主记忆文件 <100–200 行；新增一条须删或合并一条旧条；无度量标准的规则等于会被忽略的规则。
5. **规则必须可测量**："分项和=总数"（可断言）>"别写坏代码"（≈0 遵守）。
6. **强制力分层**：确定性检查 → 采样 → 模型评审 → 人审；不可逆动作必须在 hooks/CI 层强制，不依赖提示词。
7. **评审防偏差四件套**：rubric 逐项独立取证、成对比较交换顺序重跑、每维度独立评审、留"信息不足"出口；评审者不评自己的产出。
8. **失败必须回流（三选一）**：每个真实事故要么变成可测量规则（进 L1）、要么变成流程步骤/脚本（进 L2）、要么变成 hooks/门禁（进 L3）——**禁止只写进记忆完事**。
9. **完成线由合同下发**，不由执行者现场自拟。
10. **系统各层也要被审**：审核发现率异常时先审计审核器；拦截类门禁显式 fail-closed。

### 2.4 注入失效模式速查（F1–F9）

| # | 失效模式 | 机理 | 对策 |
|---|---|---|---|
| F1 | 稀释 | 规则多→每条注意力份额降 | 主文件 <100 行，只留高信号规则 |
| F2 | 位置衰减 | 中段利用率塌陷＋开头偏置 | 关键规则放文件头部；阶段边界重申 |
| F3 | 压缩蒸发 | 长会话压缩丢会话内指令 | 关键规则进文件不进对话；阶段边界重申 |
| F4 | 静默加载失败 | 扩展名/frontmatter 错 | 加载诊断；CI 校验文件格式 |
| F5 | 检索失配 | 索引词汇对不上查询 | 索引条目用"未来查询的词汇"书写 |
| F6 | 容量溢出 | 超限部分不注入 | 指针精简＋主题文件分层 |
| F7 | 层间冲突 | user/project 层矛盾 | 显式覆盖声明；定期 diff 审计 |
| F8 | 陈化污染 | 过期/矛盾条目累积 | 双周审计；长期未验证条目删除 |
| F9 | 只写不读 | 写入与读取通道不对称 | "先检索"做成流程第一步，不靠自觉 |

## 3. 回流循环（"防重复"区别于"防错"的关键）

### 3.1 闭环总图

```
错误发生 ──登记──> 错误台账（现象/根因/修复，三段键立案）
                     │
                     ▼ 三选一规则化（禁止只写进记忆完事）
      ┌─ 可测量规则（进 L1，注明注入位置与层）
      ├─ 流程步骤/脚本（进 L2）
      └─ hook/门禁（进 L3，显式 fail-closed）
                     │
                     ▼ 双通道生效
   L1 注入（下次会话"知道"）＋ L3 门禁（本次交付"必须过"）
                     │
   审核/复审发现漏检（结构化 findings）──回流──> 台账 → 新条目 → 版本号递增
```

### 3.2 回流七步（新错误：发现 → 立案 → 判层 → 归档）

1. **发现来源**：任务审核漏检｜项目复盘｜用户纠错——任一来源抓到漏检错误，当日立案。
2. **台账立案**：唯一键 = 三段式 `批次码:会话短id:E##`；字段 = 日期｜项目（P 码）｜一句话症状｜severity｜分类候选｜证据指向。
3. **判层口诀**：**去掉项目专名，规则还成立 → 通用（进全局清单）；不成立 → 专属（进项目根 1 层清单）**。例："P1 关键字段必须勾稽"去名不成立→专属；"先数明细再写总数"去名成立→通用。两可时判通用（防线更厚），台账备注"判层存疑待终审"。
4. **通用路径——并卡优先**：先 grep 触发词找既有机制卡，命中即在该卡来源行追加键＋条数 +1；无命中且同款 ≥3 条才立新卡；孤条按 severity 走单发/高危块口径。
5. **连锁重算**：正本文尾覆盖对账表逐格改新数——**数字对不平禁止合入**。
6. **重投影与落位**：机制卡层禁止手工编辑，只随数据正本机械重投影；落位后 diff 确认仅含本轮预期差异，再刷新基线登记。
7. **总索引同步＋版本号递增**：总索引对应行更新（条数/时间/状态/指向）；受影响清单头部版本号 v1 → v1.x，追加记录行写明"何时、因哪条教训、改了什么"。

**红线两条**：跳过台账立案直接改清单 = 违规回流；机制卡层只随正本重投影，任何人不例外。

### 3.3 清单增长五规矩

1. **并入优先**：新回流先找既有卡，命中即扩来源，无命中且 ≥3 条同款才立新卡；
2. **单发出入**：blocker/high 必须并卡或升高危块；low/medium 进单发表，同机制累计 ≥3 条成卡；
3. **节可增**：新大类须 ≥3 条真实错误支撑并同步路由表加行（路由表是唯一必须同步的首屏区）；
4. **对账硬约束**：覆盖对账表随每次变更重算，数字对不平禁止合入；
5. **归档冷却**：连续多个对账周期零新增且无合同引用的条目移归档文件（仍可检索到达）。

## 4. 指针文件机制全链路

这是体系日常运转的骨架：**每份文件只住一个正本，其他位置只放"指针"**，防止多副本漂移（对应 D 类"多口径并存/旧值残留"错误的机制级解法）。

### 4.1 六环链路

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 全局记忆铁律                                                       │
│    ~/.mnemon/runtime/MEMORY.md：≤6 条红线 + 1 条指针行（正本路径+版本锚）│
│    新会话开局自动注入；每条一行式，不抄清单正文（防旧值残留）              │
├─────────────────────────────────────────────────────────────────────┤
│ ② 建队前必读正本（队长纪律 T1/T2）                                     │
│    ~/.dsh/防错体系/：审核员速查清单.md（纪律正本）＋ 团队合同模板.md      │
│    ＋ 00-清单总索引.md（47 份清单的唯一登记表）                         │
│    队长建队、派任务前先读这两份，再写方案                               │
├─────────────────────────────────────────────────────────────────────┤
│ ③ 项目根 1 层清单                                                     │
│    <project-root>/1层-防错清单.md：只收项目专属教训（判层口诀判"不通用"者）│
│    开工先读第一项；条目沿用项目内编号制式，编号只增不改                   │
├─────────────────────────────────────────────────────────────────────┤
│ ④ 任务合同【清单声明】栏                                               │
│    六栏合同（工作区/任务内容/清单声明/验货/破坏性动作/项目专属清单）        │
│    【清单声明】= 适用清单版本 + 选中条目编号（G/R/T + 深查卡号）          │
│    是队长选定的"必查项·最低要求"；缺此栏整个方案作废                     │
├─────────────────────────────────────────────────────────────────────┤
│ ⑤ 审核员按清单审                                                      │
│    R1 对照选中条目逐条索要证据，缺一条打回；                            │
│    R7 增补权：审核员通读清单后自行补合同没覆盖的适用条目（双层选择防挑漏）；│
│    R5 结论只有"通过/打回"两格，打回逐条分级写明问题                     │
├─────────────────────────────────────────────────────────────────────┤
│ ⑥ 漏检回流 + 版本递增                                                 │
│    任何审核/owner 反馈抓到漏检错误 → 按回流七步蒸馏成新条目               │
│    （T5：先回写来源台账，再进清单和合同）→ 头部版本号递增                 │
│    ——防线只能越用越厚                                                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 每一环的失效模式与对策

| 环节 | 典型失效 | 对策 |
|---|---|---|
| ① 全局记忆 | 预算压缩把红线行省略；条目陈化 | 红线最小集 + 指针行，正文永不复制；双周审计 |
| ② 正本 | 多副本并存、改了副本忘改正本 | 单一正本落位，副本=留档不留引用；版本锚 = 头注版本行 + 文件时间 + 内容 hash 三元组 |
| ③ 项目根清单 | "本项目无"（其实有）；编号漂移 | 合同打回规则：项目根明明有 1 层清单却写"本项目无"→ 打回；编号只增不改 |
| ④ 清单声明 | 编号瞎写、版本不写、漏栏 | 打回规则机器化（编号 ∈ 索引键集校验）；owner 十秒核这一栏 |
| ⑤ 审核员 | 放水（"差不多就行"）| R5 两格结论 + R1 逐条索证 + 审核者≠生产者 |
| ⑥ 回流 | 跳过立案直接改清单；改卡不重算 | 回流七步硬性顺序；数字对不平禁止合入 |

### 4.3 成本实测（为什么"指针＋按需取回"而不是"全文塞上下文"）

对纪律正本的一次实测（2026-11-03，方法与原始数据见集成指南 §2）：

- 清单全文 ≈ 29K token（折算估算），其中附录区占 39% 字节且自带"执行任务禁读/禁止顺读"标注；
- 直接 grep 触发词并把命中行喂给模型：48% 的命中行落在禁读区——**全文喂入是坏姿势**；
- 按需取回：路由区（≈1.7K）＋命中 top-5 条目（≈0.8K）≈ **2.5K token，约为全文的 9%**；
- 常驻红线最小集：指针行 + ≤6 条红线 ≈ 300–400 字。

## 5. 度量与治理

- **北极星指标：错误复发率**——台账中"同根因复发"计数。每次复发 ≥2 次说明 L1 注入不够，**强制升级为 L3 硬门禁**（软约束→硬约束）。
- **健康指标（双周）**：注入健康五指标（主文件行数／规则文件数／记忆年龄／冲突数／泄露数）；台账条目"三选一"转化率 = 100%；审核证据覆盖率（已完成任务的结构化证据 100%）；审核器自审（复审发现率异常高=规格烂或评审器漂移，异常低=漏检 → 先审计审核器）。
- **三振规则**：同一问题第 3 次修复失败 → 停止修补、升级人审、质疑方案。
- **破坏性动作纪律**：删除/覆盖/外发必须单独列出"动了什么、数据去向、怎么回滚"，写清才许动手。

## 6. 边界与诚实声明

1. **824 / 91 是登记值**：源会话档案属排除区（原始语料不开源），两个量级数字只登记口径，未逐条重算。
2. **recall 实测存在同源偏置**：检索评测的查询集与清单同源（都取自同一批台账），93%–100% 的命中数字只能证明"切分后条目级检索可达"，不能证明对全新措辞任务的泛化——推广前须用独立查询集复测。
3. **门禁拦"不交证据"，拦不住"假证据"**：结构化合同字段能强制"出示打开证据"，但证据本身真不真仍靠独立审核与抽验（G2 的"真实打开"需要真证据）。
4. **规则是请求，hooks 是法律**：提示词层的遵守是概率性的；破坏性/不可逆动作（发布、删改、对外发送）必须进 L3 强制，不依赖任何提示层。
5. **体系自身也要防错**：清单条目编号一经发出永不改动、永不重排（作废标"已停用"不删号）；任何对纪律措辞、机制卡、数据的修改分别走各自的修改路由，防止"改规则时把规则改坏"。
