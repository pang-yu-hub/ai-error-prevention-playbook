# 接入指南：建队前检索清单 → 注入提示词

> 目标读者：想把这套防错体系接到自己 AI agent 工作流上的个人与团队。
> 工具无关：任何具备"系统提示/记忆文件/任务说明"概念的 agent 工具都能接。
> 实现边界：本文只讲机制与实现要点，**不附实现代码**（经 owner 确认，2026-11-17：脚本不进仓库）。
> 前置阅读：`docs/methodology.md`（四层防线与回流循环）、`playbook/` 四件模板。

---

## 0. 全链路总览

```
①把教训变成清单（判层/编号/触发场景/路由/来源标注）
        │
        ▼
②建队前检索清单（队长选卡：路由表扫表 → 检索器 → top-k 条目 + 人工确认）
        │
        ▼
③注入提示词（六栏合同【清单声明】= 必查项；全局记忆红线最小集；项目根清单开工先读）
        │
        ▼
④执行与审核（干活的人按条目自查；审核员按选中条目逐条索证 + 增补权）
        │
        ▼
⑤漏检回流（新教训 → 台账立案 → 判层 → 并卡/立卡 → 重算 → 重投影 → 版本递增）
```

## 1. 第一步：把教训变成清单

最小可用清单 = 四个设计要素（细节见 `playbook/reviewer-quick-reference.md`）：

1. **编号固定**：一经发出永不改动、永不重排；作废标"已停用"不删号。所有任务合同靠编号引用纪律，编号换义=全链断裂。
2. **触发场景放开头**：每条先一句条目名，紧跟"什么时候"说清什么场合轮到它。
3. **路由表置顶**：两张表——"任务动作路由"（你正要干的活 → 先读哪几张卡）与"症状/话术路由"（你正要说的话/眼前信号 → 先读哪几张卡）。按活跳卡，不通读。
4. **来源标注**：每条末尾写明教训出处，可回溯到错误台账。

分级结构（从上到下）：

| 层 | 内容 | 规模参考 |
|---|---|---|
| 纪律层 | 操作员 G 条 / 审核员 R 条 / 队长 T 条 + 出口自查 RL 条 | 本仓库 26 条纪律 + 13 条 RL |
| 机制层 | 失败机制卡（触发词 + 工作点/症状/正确做法/典型案例） | 本仓库 48 张 U 卡 |
| 数据层 | 逐条错误台账（键、severity、分类、证据） | 本仓库 dataset：146 条目位 / 835 教训 |

## 2. 第二步：建队前检索清单（队长选卡）

### 2.1 人工层：路由表扫表（零工具，立即可用）

队长写任务方案前，按"这个任务要干什么"扫表1、按"这个任务容易说什么错话"扫表2，各取 ≤3 张卡，写进合同【清单声明】。两表都没命中 = 登记路由缺口后关文件，**不为找相关而通读**。

### 2.2 检索器：机制与实现要点（设计正本口径）

当清单规模超过人眼扫表能力（本仓库：87 个条目单元 / 48 卡 166 个触发词 / 全文约 29K token）时，上检索器。四个机制要点全部来自一次可复现实测（见 §2.4）：

**要点一：检索单元 = 条目，不是整文件。**
按稳定正则把清单切成条目单元：纪律条目 = 单行列表项（`^- **[GRT]\d+`、`^- RL-\d+`），机制卡 = 三级标题块（`### U-` 到下一个标题）。本仓库实测：26+48+13 = 87 个单元**一次切分全中**，条目库合计约 46K 字节，可稳定作为检索单元。**永远不要把清单全文塞进上下文**（附录区占 39% 字节且自带"禁读"标注；grep 命中行 48% 落在禁读区）。

**要点二：触发词只作快速通道，不作主排序器。**
每张机制卡自带"触发:"字段（本仓库 48 卡共 166 词）。触发词与查询取交集可作预筛/加速，但**不要让 grep 命中优先决定排序**——实测"grep 优先"的两级合成把 Recall@1 从 86% 拉回 21%，并制造了唯一的完全未命中（查询词与触发词表零交集或错配时，噪声条目会把正确卡挤出前列）。

**要点三：条目级关键词打分为主，语义判官兜底。**
- 主排序：预注册关键词（每查询 4–5 个）对全部条目打分，**标题命中 ×3 ＋ 正文命中 ×1**；
- 兜底：把"一行式语义索引"（每条目一行：编号＋触发词＋一行主题＋典型案例，本仓库 87 行 ≈ 12K token）交给一个**未读过清单全文的独立模型**判读，选 top-5；
- 输出 top-k 条目全文＋命中依据（触发词命中/关键词得分/判官选择），**top-k＋人工确认，不许唯一下发**；
- **grep 命中行永不直接下发**（48% 落禁读区是实测结论）；**附录区/来源明细区永不注入**；
- 悬空引用两级展开：条目 → 映射表行 → 来源键，随条目一并取回，防"冷读者溯源断链"。

**要点四：负路由与缺口登记。**
路由表与检索器都未命中 = 本任务不在清单覆盖内：登记"路由缺口"后关文件。缺口登记是清单增长（回流）的信号源之一。

目录卡路由（多清单路由）：清单多于一份时，先建一张**总索引**（每份清单的绝对路径/条数/版本锚/指向关系），检索核第二级 = 项目路由——任务描述或当前目录命中总索引登记的项目名/目录名时，附带取回该项目根 1 层清单的条目级索引；命中未登记项目时返回"项目根清单缺失"提示并登记路由缺口。

**索引字段（只存引用，不存正文——单点真相原则）**：`id`（编号恒定）｜`title`｜`role`（operator/reviewer/captain/exit-check/mechanism）｜`scope`（global / project:<项目>）｜`task_type`（表1 动作标签 ≤3 个）｜`triggers`（触发词数组）｜`symptom_keys`（表2 话术键）｜`status`（active/deprecated）｜`version_anchor`（头注版本行+文件时间+内容 hash 三元组）｜`source_anchor`（数据正本卡 ID/正本行区间）｜`edges`（≡映射、RL→关联卡，存引用不存正文）｜`case_key`（典型案例台账键）｜`body_ref`（条目全文落点）。索引自身 = 投影产物链末端，禁手工编辑；生成时机 = 数据正本重投影后同管线再生。

### 2.3 选卡进合同：检索是建议，决策仍是人

- 检索输出 = "候选条目编号表＋命中依据"；队长人工复核增删后写入合同【清单声明】。
- 合同可加一行可选记录「选卡依据 = 检索 top-k＋人工增删说明」——给审核员增补权与事后审计留检索面证据（与"负结论必须报告检索面"同一纪律）。
- **检索建议不构成"已覆盖"证明**：审核打回依据照旧（逐条索证 + 清单外问题照常登记）。
- 编号有效性可机器校验：【清单声明】编号 ∈ 索引键集——把"编号瞎写→打回"的人工规则自动化。

### 2.4 recall 评测方法（接自家清单前先量一次）

预注册式评测，先写判分、再跑检索：

1. **查询集**：从真实错误台账/近期任务描述构造 N 条查询（本仓库实测 N=14：12 条台账案例 + 2 条近期任务），每条写明出处。
2. **应命中（预注册）**：跑检索前，按清单映射表为每条查询写定"应命中条目"（含映射依据原文）；检索实现不得读判分文件。
3. **命中定义**：应命中集合中任一条目进入排名前列；排位 = 应命中条目的最小位次；>5 记 miss。
4. **指标**：Recall@1/@3/@5 ＋ 完全 miss 数；**复算纪律：Σ分项 = 总数**（@1 命中数 + @3 内新增 + @5 内新增 = Recall@5 命中数）。
5. **语义判官盲测**：判官未读过清单全文（零污染），只读一行式索引；两位判官独立作答、互不知晓，报告一致性。
6. **同源偏置声明（必写）**：查询集若与清单同源（都取自同一批台账），93%–100% 的命中数字只能证明"切分后条目级检索可达"，**不能证明对全新措辞任务的泛化**——推广前须用独立查询集复测第二轮。

本仓库基准（供对照，N=14）：条目级关键词 Recall@5 = 13/14（93%）、Recall@1 = 12/14；条目级语义（零污染判官）Recall@1 = 14/14；整文件 grep 触发词 Recall@1 = 3/14（21%）。**结论：切分后按条目检索实证优于整文件 grep；全文喂入是坏姿势。**

## 3. 第三步：注入提示词

### 3.1 任务合同注入（每任务一层）

把六栏合同模板复制进每份任务方案（`playbook/team-contract-template.md`），其中：

- 【清单声明】= 队长选定的**必查项·最低要求**（适用清单版本 + 选中条目编号 + 可选深查卡号）；缺栏方案作废。
- 【验货】= 交付前验证步骤 + 卡路径（验证什么/用什么命令验/出示什么证据；路径之外的产出视为没验）。
- 【破坏性动作】= 没有破坏性动作就写"无"，不许空着。
- 双层选择：审核员读完清单全文后可自行增补合同没覆盖的适用条目（增补条目标注"审核员增补"），效力与合同条目相同。
- 人审关卡：owner/负责人批准时**只核【清单声明】栏**（填了没、版本对不对、编号对不对），十秒钟。

### 3.2 常驻注入：指针 + 红线最小集（每会话一层）

常驻上下文**只放指针行 + ≤6 条红线**（每条一行式，不抄清单正文——防旧值残留）：

```
指针行：清单正本路径 + 版本锚 +「跳卡不通读，先查路由表/检索」
红线1：交付文件报告完成前必须真实打开一次并出示证据（对应 G2/RL-1；用户抓错第一大类 89 条占 22%）
红线2：删除/覆盖/外发必须先列"动什么/去哪里/怎么回滚"（对应 G4/RL-10；第二大类 80 条占 20%）
红线3：数字出口先复算：Σ分项=总数（对应 G1/RL-5；数字算术类 24 条全部靠人工验算抓出）
红线4：「全部/完成/干净」出口必带对账动作（对应 G11/RL-11；覆盖面宣称 owner 抓 22 条）
红线5：断言"不存在"前必须穷举清单并二次复核（对应 G7/U-E1）
红线6：凭证/密钥不进聊天、不进记忆、不进交付（对应 RL-10；7 条漏网 100% 零抓）
```

预算参考：7 行 × 40–60 字 ≈ 300–400 字，远低于全文 29K token。常驻注入的失效模式与对策（稀释/位置衰减/压缩蒸发/静默加载失败/陈化污染等 F1–F9）见 `docs/methodology.md` §2.4。

### 3.3 项目根清单注入（每项目一层）

项目根放 `1层-防错清单.md`（模板见 `playbook/project-root-checklist-template.md`），任务合同【工作区】栏写明"开工先读"顺序：项目根清单 → 全局清单 → 点名深查卡。

## 4. DSH AgentTeams 原生接法

DeepSeek Harness（DSH）的 AgentTeams 团队模式下，本体系几乎全部机制有原生承载点：

| 体系机制 | DSH 原生承载 |
|---|---|
| 全局记忆铁律（L1） | 运行时记忆文件（`~/.mnemon/runtime/MEMORY.md`）：≤6 条红线 + 1 条指针行，新会话开局自动注入 |
| 纪律正本（L1/L2） | `~/.dsh/防错体系/`：审核员速查清单.md（正本）+ 团队合同模板.md + 回流归档流程.md + 00-清单总索引.md |
| 六栏合同（L2） | 每份任务方案复制合同模板正文；【清单声明】为 owner 十秒人审关卡 |
| 质量门（L3） | 任务级结构化合同：objective / in-scope / acceptance / verify；提交时强制 acceptanceResults + commandsRun 证据；审核 verdict 只有 pass / needs_revision 两格，打回必须带分级 findings，自动触发返修；staged 方案先交 owner Approve 再执行 |
| 独立审核（L4） | 审核者 ≠ 生产者（三分离：收集/归证/审核）；审核员独立会话，只拿交付物 + 验收标准 + 易错点清单 |
| 建队纪律（T1–T5） | 队长建队前读两份全局文件；方案必带【清单声明】；验货步骤必写；收尾核卡 + 范围审计；漏检错误必须回流 |
| 回流循环（L4→L1/L2/L3） | `~/.dsh/防错体系/回流归档流程.md`：台账三段键立案 → 判层 → 并卡/立卡 → 连锁重算 → 重投影 → 落位 → 总索引同步 + 版本递增 |
| 检索器（C 层） | 用户级 skill 渐进披露（开局只注入名称+描述目录，命中才读正文）+ 条目级索引文件 + 检索脚本（§2.2 机制要点） |

落地顺序建议：先零改动旁路（skill 披露壳 + 条目索引文件，让清单可被发现）→ 再轻改动（检索脚本 + 总索引 + 对账 lint + 正本 git 化）→ 最后插件级（动作前拦截 hooks + 结构化合同字段），每阶段验收（真实打开 + 对账全绿）通过才进下一阶段。

## 5. 任意 agent 工具通用接法

### 5.1 提示词文件注入（CLAUDE.md / AGENTS.md / 系统提示）

- 入口文件只放**指针行 + 红线最小集**（§3.2 的 7 行式），保持主文件 <100–200 行——规则越多遵守率越单调下降，注入 ≠ 遵守。
- 关键禁令放**文件头部**（中段利用率塌陷）；长任务在阶段交接处重申当阶段红线。
- 规则要**可测量**："分项和=总数"（可断言）优于"别写坏代码"（≈0 遵守）。
- 分层覆盖规范：全局层写默认，项目层显式覆盖；冲突数是健康指标（>2 即修）。
- 工具差异注意：某类 IDE 工具的 rules 目录要求特定扩展名与 frontmatter，普通 `.md` 会**静默失效**——先诊断实际加载了什么，再抱怨"不记得"。有的入口文件里列出的测试命令会被 agent 自动执行——把规则写成命令是提高遵守率的活办法。
- "先检索"做成流程第一步（skill/协议内嵌），不靠模型自觉。

### 5.2 hooks 门禁选配（L3，把"请求"升级为"法律"）

按强制力递增的四级阶梯，按需选配（机制描述，代码不随仓库分发）：

| 级 | 机制 | 强制力 | 适用 |
|---|---|---|---|
| 1 | 提示词点名检查命令 + 迭代直到通过 | 软约束 | 日常默认 |
| 2 | 会话级目标钩子（独立小判定器只凭已出示证据判定） | 半硬 | 挂机长任务 |
| 3 | 确定性 Stop hook（无模型参与；设连败封顶防死循环） | 硬门禁 | 硬性质量门 |
| 4 | 对抗式审查（新鲜上下文专门"试图推翻"；**必须限定正确性与既定需求**，否则永远能挑出毛病） | 最高 | 高风险改动 |

铁律三条：
1. **显式 fail-closed**：拦截类门禁失败必须阻断交付；各家默认多为 fail-open，是普遍陷阱——显式声明并测试拦截逻辑。
2. **不可逆动作必须进 hook/CI**：发布、删改、对外发送不依赖提示层（规则是请求，hooks 是法律）。
3. **评分器自审**：审核发现率异常时先审计审核器与任务规格，再怀疑被审对象。

CI 层可组合现成工具（公开生态，按防线选用）：确定性断言类（promptfoo 断言失败即非零退出）、合并门禁类（代码评审机器人 + 分支保护阻止合并）、编辑后自动检查类（每次 AI 编辑后自动 lint/test，破坏即回滚）、工具调用网关类（MCP 感知网关，deny→require→allow 规则，fail-closed 推荐）。选型原则：**先简单可验证，复杂度只在被证明有价值时加**；全部无需自研。

### 5.3 模型评审（LLM-as-judge）纪律

- 评审者不评自己的产出（自偏好实证）；
- rubric 逐项独立取证，不"整体扫一眼"；
- 成对比较交换顺序重跑，结果翻转即记分歧；
- 每个维度独立评审；
- 留"信息不足（Unknown）"出口，防幻觉打分；
- 与人类专家校准到分歧极小才放量。

## 6. 不做什么（反模式速查）

| # | 反模式 | 修正 |
|---|---|---|
| 1 | "你自己再检查一遍" | 换成可执行检查命令 + 证据 |
| 2 | 同会话内反复自查 | 预算花在独立评审与确定性检查 |
| 3 | 把"模型说检查过了"当证据 | 只要命令输出，不要口头保证 |
| 4 | 清单全文喂给模型 | 路由区 + top-k 条目按需注入；附录区永不注入 |
| 5 | grep 命中行直接下发 | 条目级打分为主，命中行只是线索 |
| 6 | 写无度量标准的规则 | 每条规则带触发条件 + 度量 |
| 7 | agent 自拟完成线 | 完成线由合同下发 |
| 8 | hook 默认 fail-open | 显式 fail-closed + 测试拦截逻辑 |
| 9 | 教训只写进记忆 | 三选一规则化（L1/L2/L3） |
| 10 | 一个 judge 打所有维度 | 每维度独立 + Unknown 出口 |
| 11 | 检索建议当"已覆盖"证明 | 人工复核增删 + 审核照旧打回 |

## 7. 实施路线图（P0 → P2）

## 8. 边界与诚实声明

1. **门禁拦"不交证据"，拦不住"假证据"**：结构化字段能强制出示打开证据，但证据真不真靠独立审核与抽验。
2. **recall 数字有同源偏置**（§2.4）：泛化前先独立查询集复测。
3. **提示词层遵守是概率性的**：注入 ≠ 遵守，强制力靠 hooks/CI。
4. **体系自身也要防错**：清单编号冻结、修改三路由、重投影禁手改——防止"改规则时把规则改坏"。
