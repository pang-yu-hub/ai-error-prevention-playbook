# 分类体系（taxonomy）

- 数据集：通用错误清单数据集（146条目位=48条目卡+98单发；835条通用教训，逻辑条数822；另有4条项目专属教训不入集，全库确认错误839条）
- 两个独立维度，编号不可混用：§一/§二回答「这条错误属于哪类」（A–I+Z 十大类）；§三回答「当时为什么没被拦住」（D1–D7 检测失败模式）。
- 版本依据：错误类别定义 v1.1（40条试点校准定稿）、检测失败模式分类方案（2026-10-20 定稿）。本文为机制级转写，与源定义逐句对齐。
- 类别可增：新增节须≥3条同款真实错误支撑并记录来源。

## 一、错误十类定义（A–I+Z）

### A 假完成/没验证 —— 158条教训（占835的18.9%）
- 定义：说做完没做完，或宣称所依赖的验证没跑/跑了无效。
- 判别句：产物开了吗？验证跑了吗？
- 子形态（同一类，备注可注明）：A1 宣称未做满（做了一部分/有缺陷仍宣称完成，含交付量不足）；A2 未验就宣称（写入/清理/构建后没回读、没回归就报✅）；A3 假验证通过（验证跑了但逻辑无效：空==空、计数=正确、假阴性）。
- 数据集分布：7张条目卡（卡内153行）+ 5条单发。

### B 文件/数据搞坏 —— 28条教训（占835的3.4%）
- 定义：删错、覆盖错、写坏好端端的文件/数据/系统。
- 判别句：好端端的东西被搞坏了吗？
- 数据集分布：5张条目卡（卡内28行）+ 0条单发。

### C 交付物生成缺陷 —— 18条教训（占835的2.2%）
- 定义：Excel/Word/PPT/HTML/图表等产出物本身的形态毛病（打不开/显示坏/缺列缺页/排版烂）。内容数字对错不算（→D）。
- 判别句：问题在文件形态/能否打开用吗？
- 数据集分布：3张条目卡（卡内18行）+ 0条单发。

### D 数字/口径错 —— 124条教训（占835的14.9%）
- 定义：数字算错、口径用错、两算法对不上；重算一遍能发现的都算。
- 判别句：重算一遍能发现吗？
- 数据集分布：4张条目卡（卡内115行）+ 9条单发。

### E 猜测当结论 —— 171条教训（占835的20.5%）
- 定义：没实证下结论。含：负结论没验证（说没有/查无）、单环境外推成通用、未验证前提当事实（含轻信用户口述）、想当然的机理/可行性断言。幻觉编造写进交付物=E，不是F。
- 判别句：结论是查出来的还是想出来的？
- 数据集分布：6张条目卡（卡内129行）+ 42条单发。

### F 引用/来源有假 —— 13条教训（占835的1.6%）
- 定义：编造引用、来源过期、没读原文就引。编造数值（如编造因子组分值）与编造引用同属F。
- 判别句：顺出处查得到原文吗？
- 数据集分布：3张条目卡（卡内13行）+ 0条单发。

### G 工具用法错 —— 93条教训（占835的11.1%）
- 定义：API/命令/工具手法错。三型：G1 API参数/调用用法错；G2 自研或预置脚本逻辑缺陷（使用时静默失效）；G3 无效偏方操作。
- 判别句：是用工具的手法错了吗？
- 数据集分布：3张条目卡（卡内93行）+ 0条单发。

### H 理解偏差/指令遵循 —— 112条教训（占835的13.4%）
- 定义：理解错需求/指令/概念。含：违抗明示指令、漏做需求、超口径交付、把「没有」误当「缺失」等概念性理解错。
- 判别句：是需求/指令/概念理解错吗？（干活顺序/循环失控→I）
- 数据集分布：5张条目卡（卡内106行）+ 6条单发。

### I 流程失控/无效循环 —— 102条教训（占835的12.2%）
- 定义：同一个坑反复踩、无效循环不换道、作用域/节奏失控、反常信号不触发路线重估、违反已沉淀纪律。
- 判别句：是干活顺序/循环失控的问题吗？（一次性的需求理解错→H）
- 数据集分布：6张条目卡（卡内70行）+ 32条单发。

### Z 长尾杂项 —— 16条教训（占835的1.9%）
- 定义：以上都不是的单发。占比>5%须修定义。
- 判别句：（源定义未设判别句：Z 为兜底类）
- 数据集分布：6张条目卡（卡内12行）+ 4条单发。

## 二、防吞并细则

### 2.1 A 类防吞并细则

A 的「没验证」仅指该验证节点是宣称的一部分（说完成/说通过/说一致/说在跑）。操作后顺带没主动复核不升 A，按操作手法归 G/H/I。

### 2.2 分界规则速查（9 对易混类）

| 纠结对 | 分界 |
|---|---|
| A vs E | 做出来了没验→A；结论没实证（含说没有）→E |
| A vs G | 验证节点属于宣称→A；仅操作手法错+顺带没复核→G |
| A vs B | 以搞坏既有好数据为主→B；以宣称完成/验过为主→A（横跨取A） |
| B vs G | 搞坏了→B；仅手法错未造成破坏→G |
| C vs D | 文件坏/缺/显示坏→C；数不对→D |
| D vs F | 算错/口径错→D；来源假/编造→F |
| E vs F | 结论无实证→E；出处造假/编造→F |
| G vs I | 一次手法错→G；反复循环不换道/违反纪律→I |
| H vs I | 需求/指令/概念理解错→H；干活顺序/循环失控→I |

### 2.3 横跨优先级

一条错误跨多类时，主类按 **A>B>E>D>C>F>G>H>I>Z** 取前，第二候选写备注。

### 2.4 通用/项目专属判定口诀

- 口诀：这个坑换个项目还会踩吗？把规则里的项目专名去掉，仍成立→通用；不成立→项目专属。
- 模式本身通用，即使案例发生在某项目，也算通用；依赖项目特定事实（特定文件/口径/系统行为）才是专属。
- 口径注记：本数据集采用清单层定稿口径=通用 835 + 项目专属 4（专属4条不入集）；源数据表的 generality 参考字段（疑似通用831/仅本项目8）为另一层口径，两者合计均为839、不矛盾。

## 三、D1–D7 检测失败模式（当时为什么没被拦住）

- 数据底座：全库839条确认错误按发现渠道切分——用户(owner)当时亲手纠出414条（49.3%），当时没人发现425条（其中「事后挖掘才翻出」348条）。
- 对348条蒸馏出「AI 该拦没拦住」的检测失败模式；统一判定问题：**如果当时有哪道机制，这条错误当场就会被拦下？** 取「最接近交付时点、最后一道本可拦住它的网」，单选主模式。
- 编号说明：定稿表编号不连续（无 D6/D7b 条目），按源方案呈现，非缺漏。

### 3.1 模式定义与判别句

| 模式 | 定义 | 判别句 |
|---|---|---|
| **D1 假完成-未验证** | 打开产物/跑一次真实使用即可发现；含「当场可见证据已矛盾仍继续宣称通过」（Traceback/空输出/Σ≠总数已回显仍写✅/todo 私翻 completed 后继续推进） | 产物开了吗？跑了？ |
| **D2 验证器失效** | 验证动作发生了，但验证器自己的对象/实现/标准错了（比值冒充产量、du -sb 空==空判等、旧校验器当权威、自验脚本与生成器不共源） | 验证动作本身错了吗？ |
| **D3 缺对照物** | 验证动作对，但没拿外部基准（因子库/官方清单/权威文档/参考实现/底稿/行业区间），当时拿得到；子型 D3b=真值当时真拿不到（仅后续运行/对方闭环可知，如用预发环境外推生产） | 对照物在吗？拿得到吗？ |
| **D4 验收信息缺口** | 只有用户知道的信息才能判（需求对齐/口味/验收标准）；与 D1 冲突时 D1 优先 | 这事只有owner能判吗？ |
| **D5 静默副作用** | 删/覆盖/写入/外发无回显无确认；含第三方库静默行为（openpyxl 丢 sheet）、后台任务假成功（rsync/robocopy 无报错≠成功）、凭据静默落盘 | 副作用回显了吗？确认了吗？ |
| **D7a 规则空白-高危** | 当时无红线覆盖且造成实际损失/风险（泄露、生产误删）；报错当场可见的过程摩擦不属此类（→X0）；事后新立的规则禁止当「当时无规则」的证据 | 当时有这条红线吗？ |
| **X0 过程损耗（噪声桶）** | 报错当场可见的过程性摩擦（命令连败/内联试错/零响应中断）——不存在本可拦住的网，属登记噪声而非检测失败 | 这真是检测失败吗？ |

### 3.3 成文分界（解决跨组口径漂移，共4条）

1. Excel 占用写入失败 37(D1) vs 占用期直写覆盖 146/275/57/87(D5)：分界=写入是否实际生效/是否覆盖用户数据
2. 删除类「删错对象」(D1/D3) vs「未确认就删」(D5)：分界=错在选型还是错在流程
3. 验证器家族按失败面拆分：matcher 自身缺陷(D2) vs 未对照平台定义(D3) vs 对照表未逐条核(D1)
4. 「审计门拦截」只认审核实锤，「吸收注记」不算；「用户发现」从严=用户消息直接指认/当场撞错，泛化提问由 AI 查实的归自查抓出

### 3.4 错误最终怎么浮出水面（catch_stage，基数348）

| 浮出渠道 | 条数 | 说明 |
|---|---|---|
| 事后挖掘 | 186 | 复盘项目通读原文才翻出（真正的「网全漏」主体） |
| 自查抓出 | 84 | AI 会话内自查/终检发现并披露——网是工作的 |
| 用户发现 | 54 | 标签噪声：用户当时就发现；抽严后 47 条站得住 |
| 审计门拦截 | 20 | 审核 agent/对账员当场拦住——网是工作的 |
| 未拦截 | 4 | 持续到会话结束零注意（含规避检测器的 1 条） |

**核心发现：348 的基数本身虚高。** 抽严后真实构成 ≈ **真实检测失败 247 条**（事后挖掘186 + 未拦截4 + 用户发现中经复核仍属漏检约57）+ **网其实工作正常的 104 条**（自查84 + 审计门20）+ **登记噪声约 50 条**（用户发现54中与自查重叠部分、X0 45 全部）。防错资源应集中在真实漏检上，而非348全量。

### 3.5 对策映射（五塞子：7类伤口只用5个塞子堵）

| 对策 | 治哪个洞 | 干什么 |
|---|---|---|
| 塞子1 交付前检查 | D1（178条≈51%，第一优先） | 每类交付物配交付前必做清单：文件真实写盘+真实打开+分项和=总数断言；同消息出现过报错就不许说✅完成 |
| 塞子2 开工先找裁判 | D3（61条≈18%） | 动手前先回答「这条产物的对错，裁判是谁？在哪」（官方文档/底稿/参考库），答案写进方案才动手 |
| 塞子3 破坏性动作单独确认 | D5（31条≈9%） | 删/覆盖/外发单独一条列出：动什么、数据去哪、怎么回滚；后台任务双信号确认（退出码+产物在） |
| 塞子4 验证器先自测 | D2（16条≈5%，错了最疼） | 自查前先三问：尺子的对象对吗？实现对吗？跟干活的是不是同一把尺子（共源=白查） |
| 塞子5 硬红线+机器门禁 | D7a（9条≈3%，单条最疼） | 泄露必吊销/生产操作先验快照/打包先查忽略清单，评估做成「不过就交不出去」的机器门 |
| 附：高频摩擦脚本化 | X0（45条噪声） | 反复出现的命令级坑（重试/引号/编码）沉淀为可复用脚本，不靠记住 |

最大的一个塞子是**交付前检查**：能挡住约一半漏检（D1 的178条）。

## 四、使用建议

- 给 AI 注入时：十类定义+判别句做「事后归类」用；防吞并细则做「打标一致性」用；D 模式+五塞子做「事前拦截」用（把对应塞子变成交付前的固定检查步骤）。
- 引用本数据集时请注明：146条目位/835教训（逻辑条数822）、全库839条确认错误、severity 分布 blocker9/high131/medium314/low385。
